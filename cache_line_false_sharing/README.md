## Execute and generate the submission

From this directory, using Python 3.13 and a host with four available physical
CPU cores:

```sh
python -m pip install -r requirements.txt
python run_lab.py
```

One command runs four pinned native threads for **60,000,000 updates per thread**
in each of four stride layouts and a register-private baseline. Each layout is
repeated three times. It then writes the telemetry and LLVM evidence, generates
ANALYSIS.md from this run's exact measurements, and verifies the result.

For Jupyter or Google Colab, open the repository's
[notebook](../cache_line_false_sharing_lab.ipynb). It installs dependencies, checks
the host, runs the same command, displays the report, and offers a ZIP download.
Colab may provide fewer than four physical cores; the hardware check will explain
why such a runtime cannot satisfy the lab. No simulated results are substituted.

The included artifacts are a real earlier Windows run. The runner overwrites
them with your own run. To verify the included evidence without benchmarking:

```sh
python verify_submission.py
```

To repeat the workload more times, use `python run_lab.py --repeats 5`.
The handle defaults to ros1nant and is bound to the CPU model at runtime.

For a quick smoke check that preserves the submitted measurements:

```sh
python false_sharing_lab.py --iterations 2000000 --repeats 1 --output-dir smoke-output
```

A smoke manifest intentionally has `verification_passed: false` because it did
not perform the required 60,000,000 updates per thread.

## Platform details

Linux reads physical-core topology from sysfs, pins individual workers with
sched_setaffinity, and reads voluntary/involuntary context switches with
resource.getrusage. Windows uses GetLogicalProcessorInformation and
SetThreadAffinityMask. Its resource module is unavailable, so only a psutil total
is recorded, and the two unavailable categories are null. The report explicitly
explains this limitation. Workers stay alive during both telemetry snapshots.

The submitted implementation requires four identifiable physical cores, 64-byte
cache lines, and per-thread affinity. It fails clearly when these are unavailable.
Windows processor groups above 64 logical CPUs and macOS per-thread affinity are
not supported by this implementation. Pure timing does not prove individual RFO
events or a particular prefetcher mechanism.
